🎯 TUJUAN & SILABUS

Capaian Pembelajaran (Sub-CPMK 13)

Mahasiswa mampu mengidentifikasi code smell, merekayasa arsitektur berstandar SOLID, dan menerapkan decoupling dependensi dengan PHP 8+.

📋 5 Prinsip Desain SOLID

  • S — Single Responsibility Principle (SRP): Satu class, satu alasan perubahan.
  • O — Open/Closed Principle (OCP): Terbuka untuk ekstensi, tertutup untuk modifikasi.
  • L — Liskov Substitution Principle (LSP): Subtipe harus dapat menggantikan Parent.
  • I — Interface Segregation Principle (ISP): Antarmuka ramping berbasis peran spesifik.
  • D — Dependency Inversion Principle (DIP): Bergantung pada abstraksi, bukan konkrit.

💡 Dampak bagi Rekayasa Enterprise

Menerapkan SOLID mengubah arsitektur rapuh menjadi sistem kelas industri yang tangguh:

  • Menghilangkan keterikatan ketat (*Tight Coupling*) antar komponen sistem.
  • Fitur baru dapat ditambahkan tanpa memodifikasi atau menguji ulang kode lama.
  • Memungkinkan Unit Testing 100% menggunakan Mocking Objects secara instan.
⚠️ MASALAH ARSITEKTUR

Bahaya Software Rot (Pembusukan Kode)

4 Gejala utama aplikasi yang tidak mematuhi prinsip desain objek (Robert C. Martin).

1. Rigidity (Kekakuan)

Setiap perubahan kecil pada satu baris kode menuntut perubahan berantai di puluhan berkas modul lain.

2. Fragility (Kerapuhan)

Memperbaiki bug di modul A justru memicu kerusakan fatal pada modul Z yang tidak terkait logika.

3. Immobility (Ketakbergerakan)

Komponen tidak bisa dipindahkan atau digunakan kembali di proyek lain karena terikat dependensi rumit.

4. Viscosity (Viskositas)

Struktur kode begitu rumit sehingga programmer memilih membuat jalan pintas buruk (*hack*) daripada taat arsitektur.

Visi SOLID: Menghasilkan perangkat lunak yang elastis terhadap perubahan bisnis, mudah dipahami tim, dan memiliki biaya perawatan jangka panjang (*maintenance cost*) yang rendah.
1️⃣ HURUF S DARI SOLID

S — Single Responsibility Principle (SRP)

"Sebuah kelas hanya boleh memiliki satu, dan hanya satu, alasan untuk berubah."

❌ Antipattern God Object

Class Pesanan mengurus kalkulasi diskon, query database MySQL, generate PDF, dan kirim email sekaligus.

class Pesanan { public function hitungTotal() {} public function simpanKeDatabase() {} public function cetakInvoicePdf() {} public function kirimNotifikasiEmail() {} }

✅ Refactored SRP Berbasis Aktor

Setiap tanggung jawab didelegasikan ke class spesialis yang terfokus:

  • Pesanan → Memegang entitas & invariant bisnis.
  • PesananRepository → Persistensi data.
  • InvoicePdfPrinter → Formatting dokumen cetak.
  • EmailNotifier → Komunikasi eksternal.
2️⃣ HURUF O DARI SOLID

O — Open/Closed Principle (OCP)

"Terbuka untuk perluasan fitur (*Extension*), tetapi tertutup untuk modifikasi kode lama (*Modification*)."

📌 Bahaya Modifikasi Percabangan:

Menambah jenis diskon baru dengan mengedit switch-case berisiko merusak kalkulasi diskon yang sudah teruji sebelumnya.

// ❌ OCP Melanggar: Ubah kode lama tiap ada diskon baru if ($tipe === VIP) return $subtotal * 0.2; if ($tipe === MEMBER) return $subtotal * 0.1; // Tambah FLASH_SALE? Harus edit & test ulang file ini!

✅ Solusi OCP: Strategy Pattern

Buat antarmuka DiskonStrategyInterface. Fitur diskon baru cukup dibuat di class terpisah tanpa menyentuh class Service!

interface DiskonStrategyInterface { public function hitungDiskon(float $total): float; } class DiskonFlashSale implements DiskonStrategyInterface { public function hitungDiskon(float $total): float { return $total * 0.50; // ✨ Class baru tanpa ubah kode lama } }
3️⃣ HURUF L DARI SOLID

L — Liskov Substitution Principle (LSP)

"Objek dari kelas turunan harus dapat menggantikan objek kelas induknya tanpa merusak kebenaran program."

⚠️ Contoh Pelanggaran Klasik LSP:

Class anak mengubah perilaku yang diharapkan dari class induk atau melempar exception tak terduga:

class ReadOnlyDocument extends Document { public function save(): void { // 💥 Melanggar LSP: Melempar error tak terduga bagi pemanggil throw new \LogicException("Dokumen read-only tidak bisa disimpan!"); } }

✅ Aturan Penegakan LSP di PHP 8+:

  • Aturan Tipe Balikan (*Covariance*): Subclass boleh mengembalikan tipe yang lebih spesifik, tetapi tidak boleh lebih umum.
  • Aturan Parameter (*Contravariance*): Subclass boleh menerima tipe argumen yang lebih umum.
  • Integritas Kontrak: Jangan pernah mempersempit kemampuan yang dijanjikan oleh class induk/interface.
4️⃣ HURUF I DARI SOLID

I — Interface Segregation Principle (ISP)

"Klien tidak boleh dipaksa bergantung pada antarmuka (*Interface*) yang tidak mereka gunakan."

❌ Masalah "Fat Interface"

Interface gemuk memaksakan implementasi method kosong atau dummy pada class yang tidak membutuhkannya:

interface PrinterInterface { public function print(); public function scan(); public function fax(); } // ⚠️ Printer Biasa dipaksa implementasi fax() kosong!

✅ Solusi "Role-based Interfaces"

Pecah interface menjadi antarmuka kecil yang fokus pada kapabilitas tunggal:

interface Printable { public function print(); } interface Scannable { public function scan(); } class PrinterBiasa implements Printable { public function print() { /* ... */ } }
5️⃣ HURUF D DARI SOLID

D — Dependency Inversion Principle (DIP)

"Modul tingkat tinggi tidak boleh bergantung pada modul tingkat rendah. Keduanya harus bergantung pada Abstraksi."

📌 Mengapa Hardcoded Dependency Berbahaya?

Jika class CheckoutService langsung melakukan instansiasi new MidtransPayment() di dalam kodenya, maka aplikasi terikat mati pada satu vendor payment gateway dan mustahil diuji (*unit test*) tanpa kartu kredit riil!

Inversi Ketergantungan via Interface
// 1. Abstraksi Kontrak Pembayaran interface PaymentGatewayInterface { public function bayar(float $jumlah): bool; } // 2. Modul Tingkat Tinggi Bergantung pada Abstraksi class CheckoutService { public function __construct( private PaymentGatewayInterface $payment ) {} }
🚀 PHP 8.0+ CONSTRUCTOR PROMOTION

Modern Dependency Injection (DI)

Menyuntikkan dependensi secara deklaratif melalui Constructor Property Promotion.

App/Service/AkademikService.php
<?php namespace App\Service; use App\Domain\Repository\MahasiswaRepositoryInterface; use App\Domain\Service\NotifierInterface; class AkademikService { // ✨ PHP 8.0+: Deklarasi properti & injeksi dependensi dalam 1 langkah! public function __construct( private readonly MahasiswaRepositoryInterface $repository, private readonly NotifierInterface $notifier ) {} public function daftarkanMahasiswa(Mahasiswa $mhs): void { $this->$repository->simpan($mhs); $this->$notifier->kirim("Selamat bergabung, {$mhs->nama}!"); } }
Kemudahan Testing: Pada unit test PHPUnit, kita dapat menginjeksi MockMahasiswaRepository tanpa perlu menyentuh disk fisik server!
🛒 STUDI KASUS INTEGRASI 5 PRINSIP

Integrasi Penuh SOLID: Sistem Checkout

Harmoni SRP, OCP, LSP, ISP, dan DIP dalam satu alur transaksi e-commerce yang bersih.

App/Service/CheckoutService.php
class CheckoutService { public function __construct( private readonly OrderRepositoryInterface $orderRepo, private readonly PaymentGatewayInterface $gateway, private readonly NotifierInterface $notifier ) {} public function proses( Order $order, DiskonStrategyInterface $diskon ): void { $potongan = $diskon->hitungDiskon($order->subtotal); $finalTagihan = $order->subtotal - $potongan; $this->gateway->bayar($finalTagihan); $this->orderRepo->simpan($order); $this->notifier->kirim("Pesanan {$order->id} Berhasil!"); } }

✨ Bedah Arsitektur:

  • SRP: Service hanya orkestrasi alur checkout.
  • OCP: Diskon baru = class baru (DiskonRamadhan).
  • LSP: Gateway apa pun (Midtrans/Xendit) dapat ditukar bebas.
  • ISP: Notifier hanya mewajibkan method kirim().
  • DIP: Seluruh dependensi berbasis Interface.
📋 CHECKLIST REKAYASA

Panduan Cepat Audit Kualitas Kode SOLID

Kenali bau kode buruk (*Code Smells*) dan lakukan tindakan perbaikan (*Refactoring*) presisi.

🚨 Gejala Bau Kode (Code Smells):

  • Class memiliki lebih dari 300 baris dan puluhan method heterogen.
  • Banyak blok switch-case memeriksa string tipe diskon/pembayaran.
  • Class anak melempar NotImplementedException pada method warisan.
  • Instansiasi langsung new ClassKonkrit() di dalam konstruktor.

🛠️ Solusi Perbaikan Berstandar SOLID:

  • Pecah menjadi class-class kecil berbasis peran tunggal (**SRP**).
  • Gunakan pola **Strategy Pattern** via Interface (**OCP**).
  • Evaluasi hierarki warisan dan patuhi kontrak interface (**LSP**).
  • Injeksi dependensi interface via Constructor Promotion (**DIP**).
