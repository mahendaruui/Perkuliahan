⭐ Star Schema

Fact di Tengah, Dimension di Sekeliling

Fact hanya terhubung langsung ke dimensi — tanpa join antar-dimensi:

📊 Fact Table
Foreign key + measure. Jutaan baris. Contoh: `fact_sales`.
📅 Dimension
Konteks deskriptif: date, product, customer, store.
📏 Grain
Makna satu baris fact. Contoh: satu item pesanan.
🔢 Measure
Angka yang dianalisis: quantity, revenue, margin.
✅ Star schema lebih mudah dipahami pengguna BI dan biasanya lebih cepat untuk query analitik.

🗂️ Dimension Table

Surrogate Key vs Natural Key

Fact menyimpan integer key; natural key tetap disimpan di dimensi untuk traceability:

AspekSurrogate KeyNatural Key
BentukInteger berurutanKode bisnis (text)
StabilitasTidak berubahBisa berubah
Kinerja joinCepatLebih lambat
Mendukung SCDYaTidak cocok
💡 Gunakan surrogate key di fact. Simpan natural key di dimension untuk audit dan lookup.

07 / 17
➕ Additivity

Tidak Semua Angka Boleh Dijumlahkan

Kesalahan agregasi menghasilkan laporan yang salah meski query-nya “jalan”:

TipeDapat DijumlahkanContohPerlakuan
AdditiveSemua dimensiRevenue, quantitySUM() aman
Semi-additiveSemua kecuali waktuSaldo stok, saldo bankRata-rata/akhir periode
Non-additiveTidakRasio, persentase, hargaHitung dari pembilang/penyebut
-- ❌ Salah: menjumlahkan persentase
SELECT SUM(margin_pct) FROM fact_sales;

-- ✅ Benar: hitung dari agregat
SELECT SUM(margin) / NULLIF(SUM(net_revenue), 0) AS margin_pct
FROM fact_sales;
08 / 17
🧩 Dimensi Khusus

Degenerate, Junk, Role-Playing

Tiga pola yang muncul di hampir semua data warehouse:

🔢 Degenerate Dimension
Nomor dokumen (`order_id`, `invoice_no`) disimpan langsung di fact, tanpa tabel dimensi.
🧷 Junk Dimension
Kombinasi flag kecil (`is_gift`, `is_promo`, `channel`) dalam satu tabel.
🎭 Role-Playing
Satu dimensi berperan beberapa kali: order_date, ship_date, delivery_date.
🌉 Bridge Table
Relasi many-to-many, mis. produk–supplier, dengan bobot alokasi.

📅 DDL Dimensi

Tanggal, Produk, Pelanggan, Toko

Setiap dimensi memiliki surrogate key dan natural key yang unik:

CREATE TABLE dw.dim_product (
    product_key   BIGSERIAL PRIMARY KEY,
    product_code  TEXT NOT NULL UNIQUE,
    product_name  TEXT NOT NULL,
    category      TEXT NOT NULL,
    subcategory   TEXT,
    cost          NUMERIC(12,2) NOT NULL DEFAULT 0
);

CREATE TABLE dw.dim_customer (
    customer_key  BIGSERIAL PRIMARY KEY,
    customer_code TEXT NOT NULL UNIQUE,
    customer_name TEXT NOT NULL,
    city          TEXT,
    segment       TEXT
);

CREATE TABLE dw.dim_date (
    date_key    INTEGER PRIMARY KEY,
    full_date   DATE NOT NULL UNIQUE,
    year        INTEGER NOT NULL,
    quarter     INTEGER NOT NULL,
    month       INTEGER NOT NULL,
    day_of_week INTEGER NOT NULL,
    is_weekend  BOOLEAN NOT NULL
);

📊 DDL Fact

Foreign Key + Measure + Degenerate Dimension

Unique constraint `(order_id, line_no)` menjaga grain dan idempotensi:

CREATE TABLE dw.fact_sales (
    sales_key     BIGSERIAL PRIMARY KEY,
    date_key      INTEGER NOT NULL REFERENCES dw.dim_date(date_key),
    product_key   BIGINT  NOT NULL REFERENCES dw.dim_product(product_key),
    customer_key  BIGINT  NOT NULL REFERENCES dw.dim_customer(customer_key),
    store_key     BIGINT  NOT NULL REFERENCES dw.dim_store(store_key),
    order_id      TEXT NOT NULL,
    line_no       INTEGER NOT NULL,
    quantity      INTEGER NOT NULL CHECK (quantity > 0),
    gross_revenue NUMERIC(14,2) NOT NULL,
    discount      NUMERIC(14,2) NOT NULL DEFAULT 0,
    net_revenue   NUMERIC(14,2) NOT NULL,
    cost          NUMERIC(14,2) NOT NULL DEFAULT 0,
    margin        NUMERIC(14,2)
        GENERATED ALWAYS AS (net_revenue - cost) STORED,
    UNIQUE (order_id, line_no)
);

CREATE INDEX idx_fact_sales_date
    ON dw.fact_sales(date_key);
CREATE INDEX idx_fact_sales_product
    ON dw.fact_sales(product_key);

📥 Load Fact

Lookup Surrogate Key Saat Load

Fact tidak menyimpan kode produk/pelanggan; ia menyimpan key hasil join:

INSERT INTO dw.fact_sales (
    date_key, product_key, customer_key, store_key,
    order_id, line_no, quantity,
    gross_revenue, discount, net_revenue, cost
)
SELECT
    TO_CHAR(o.order_ts::TIMESTAMP, 'YYYYMMDD')::INT,
    p.product_key,
    c.customer_key,
    s.store_key,
    o.order_id,
    ROW_NUMBER() OVER (PARTITION BY o.order_id
                       ORDER BY o.product_code)::INT,
    o.quantity::INT,
    o.quantity::NUMERIC * o.unit_price::NUMERIC,
    COALESCE(o.discount::NUMERIC, 0),
    o.quantity::NUMERIC * o.unit_price::NUMERIC
        - COALESCE(o.discount::NUMERIC, 0),
    o.quantity::NUMERIC * p.cost
FROM staging.raw_orders o
JOIN dw.dim_product p  ON p.product_code = o.product_code
JOIN dw.dim_customer c ON c.customer_code = o.customer_code
JOIN dw.dim_store s    ON s.store_code = o.store_code
WHERE o.status = 'paid';

✅ Validasi

Tiga Query untuk Membuktikan Skema Benar

Revenue kategori, tren bulanan, dan margin yang dihitung dengan benar:

SELECT p.category,
       SUM(f.net_revenue) AS revenue,
       SUM(f.quantity)    AS units
FROM dw.fact_sales f
JOIN dw.dim_product p ON p.product_key = f.product_key
GROUP BY p.category
ORDER BY revenue DESC;

SELECT d.year, d.month, SUM(f.net_revenue) AS revenue
FROM dw.fact_sales f
JOIN dw.dim_date d ON d.date_key = f.date_key
GROUP BY d.year, d.month
ORDER BY d.year, d.month;

SELECT p.category,
       SUM(f.margin) / NULLIF(SUM(f.net_revenue), 0) * 100
           AS margin_pct
FROM dw.fact_sales f
JOIN dw.dim_product p ON p.product_key = f.product_key
GROUP BY p.category;

🎮 Refleksi

Kuis Kilat 3 Menit

Jawab dulu, lalu klik untuk membuka jawaban:

❓ Mengapa fact table menyimpan surrogate key, bukan kode produk?
✅ Surrogate key integer lebih cepat untuk join, stabil meski kode bisnis berubah, dan mendukung banyak versi dimensi (SCD).
❓ Apa contoh measure non-additive?
✅ Persentase margin, rasio konversi, harga satuan. Jangan dijumlahkan; hitung dari agregat pembilang dan penyebut.
❓ Apa fungsi unique constraint (order_id, line_no) di fact?
✅ Menjaga grain agar satu baris mewakili satu item pesanan, sekaligus memungkinkan upsert/idempotensi saat ETL dijalankan ulang.
