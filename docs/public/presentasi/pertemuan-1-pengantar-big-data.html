⚠️ Miskonsepsi

Volume Bukan Satu-satunya Ukuran

Arsitektur ditentukan oleh pola akses dan SLA, bukan angka volume semata:

🏪 Data Kecil, Cepat
5.000 transaksi/detik tetap menantang karena velocity dan kebutuhan latensi.
🗄️ Data Besar, Jarang Diakses
100 TB arsip mungkin cukup di object storage murah tanpa cluster komputasi besar.
📈 Data Sedang, Bertumbuh
Rancang untuk 2–3 tahun ke depan, bukan hanya kebutuhan bulan ini.
🔍 Kuncinya: Pola Akses
Query harian, retensi, puncak beban, dan toleransi keterlambatan menentukan teknologi.

🕰️ Evolusi

Lima Generasi Platform Data

Setiap generasi menjawab keterbatasan generasi sebelumnya:

1
1970 — RDBMS

Model relasional Codd: integritas transaksi, SQL, normalisasi.

2
1990 — Data Warehouse

Inmon & Kimball: gudang data terpusat untuk BI dan OLAP.

3
2006 — Hadoop

GFS + MapReduce: penyimpanan & komputasi terdistribusi di hardware murah.

4
2009–2011 — Spark & Kafka

Pemrosesan in-memory dan log event real-time.

5
2020+ — Lakehouse

Delta Lake, Iceberg, Hudi: ACID + tata kelola di atas data lake.

🏗️ Arsitektur

Enam Lapisan Platform Data

Setiap lapisan punya tanggung jawab dan alat yang berbeda:

📥 1. Ingestion
Batch connector, CDC, Kafka. Menarik data dari sumber tanpa membebani sistem transaksi.
💾 2. Storage
Bronze → Silver → Gold. Object storage + format kolumnar + katalog.
⚙️ 3. Processing
Spark, Hive, stream processor. Transformasi, join, agregasi, ML.
📤 4. Serving
Warehouse, NoSQL, cache, API, dashboard. Melayani konsumen data.
🔁 5. Orkestrasi
Airflow/Dagster: jadwal, dependensi, retry, backfill, alert.
🛡️ 6. Governance
Katalog, lineage, kualitas, keamanan, privasi, biaya, observabilitas.

🧮 Estimasi

Back-of-the-Envelope yang Wajib Dikuasai

Contoh: 5 juta event/hari × 800 byte, retensi 1 tahun, replikasi 3×, Parquet 4× lebih kecil:

mentah/hari   = 5.000.000 x 800 B  ~= 4 GB
mentah/tahun  = 4 GB x 365        ~= 1,46 TB
Parquet (1/4) = 1,46 TB / 4       ~= 0,37 TB
replikasi 3x  = 0,37 TB x 3       ~= 1,1 TB
💡 Kesimpulan
Storage biasanya bukan bottleneck utama. Yang mahal adalah komputasi, shuffle, dan operasional.
⚠️ Jangan lupa: overhead metadata, small files, pertumbuhan data, biaya egress, retensi PII, dan puncak beban.

🎮 Refleksi

Kuis Kilat 3 Menit

Jawab dulu, lalu klik untuk membuka jawaban:

❓ Mengapa data 5.000 transaksi/detik bisa disebut big data meski volumenya tidak besar?
✅ Karena velocity-nya tinggi. Sistem harus menyerap dan merespons dalam hitungan milidetik; solusinya berbeda dari batch harian.
❓ Kapan RDBMS tetap pilihan terbaik?
✅ Saat data relasional, transaksi multi-tabel penting, volume masih wajar, dan tim butuh konsistensi kuat. Jangan memaksakan NoSQL tanpa alasan.
❓ Apa risiko utama jika memilih streaming tanpa kebutuhan latensi?
✅ Kompleksitas operasional naik: checkpoint, exactly-once, rebalancing, monitoring lag — tanpa manfaat bisnis yang sepadan.
